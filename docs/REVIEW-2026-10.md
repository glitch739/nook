# Performance and code review — 2026-10-02

A pass over the whole backend and frontend, asked for by the user:
what can be improved or refactored, and what would make Nook faster
and more fluid. **Items 1–3 were implemented the same evening (see
"Done" below); the rest is still open.** Each item says what
was measured or found, what to change, the expected effect, and a
rough effort (S = under an hour, M = a few hours, L = a day or more).

## How this was measured

On a copy of the real data restored from a backup (3 users, 111 pages,
21 spaces, 9 images), served by the current Docker image on this
server, measured with curl and headless Chromium on the same machine.
Same-machine numbers have no network latency, so on a phone over the
internet everything that depends on bytes transferred gets worse.

| Measurement | Result |
|---|---|
| API calls (`/api/me`, `/api/spaces`, one space tree, database rows) | 2–6 ms each |
| Startup: requests / bytes transferred | 28 / 1.27 MB |
| Startup: sidebar visible after | 876 ms |
| First page opened (loads the editor) | 899 ms |
| Switching to another page | 202 ms |
| Main JS bundle | 1.20 MB raw, 300 KB if gzipped |
| Editor JS chunk | 499 KB raw, 161 KB if gzipped |
| Responses compressed | none (no gzip/brotli anywhere) |
| JS heap after load | 11 MB |

**Conclusion: the backend is not the bottleneck.** Every API call
answers in a few milliseconds. The time goes into shipping and parsing
large uncompressed JavaScript, and into a few sequential waits on page
open. The biggest wins are on the frontend delivery side, and most of
them are small changes.

## Done — 2026-10-02 (items 1–3)

Measured on the same restored data, old image vs new, page-open time
taken inside the page (MutationObserver), not by the test tool:

| Measurement | Before | After |
|---|---|---|
| Main JS bundle | 1198 KB raw | 260 KB raw, 67 KB on the wire (brotli) |
| Startup bytes on the wire | 1.27 MB | ~0.38 MB |
| First page opened, editor visible | ~550 ms | ~210–240 ms |
| Files in the build | 4164 | 2088 |

What changed:
- Precompressed `.br`/`.gz` assets (`scripts/precompress.sh` in the
  image build), served by `internal/webui` when accepted, plain file
  otherwise; gzip for JSON API responses of 1 KB or more
  (`httpapi/compress.go`).
- Icons served from `/assets/lucide-<version>/<name>.svg` by a Vite
  plugin; `iconSvg.ts` is the only icon code in the main bundle; the
  name list and search tags live in the lazy IconPicker chunk.
- `collabUser.ts` split out so Yjs loads with the editor chunk.
- Editor and database chunks preloaded after login, through
  `preloadable.tsx`, which also removes React's 300 ms minimum
  Suspense fallback once a chunk is in memory. That 300 ms, not the
  download, was most of the first-open delay.

Not changed on purpose: the page-open sequence in `App.tsx` that
waits for `GET /api/pages/{id}` before mounting the editor. It guards a
fixed data-loss race; with the delay above gone it is no longer the
bottleneck.

Verified: Go tests incl. new webui/compress tests; in a browser on the
real-data copy: sidebar icons, icon picker and search, typing + reload
persistence, realtime edit seen on a second (phone) client, database
view, no page errors. Known and unrelated: a 404 in the console for
`/cover/meta` on pages without a cover (also in the old build).

## Speed: biggest effect for the least work

### 1. Compress responses (S)
Nothing is compressed today: the browser downloads the 1.2 MB main
bundle as 1.2 MB. Precompress the embedded build at image build time
(`.br` and `.gz` next to each asset) and serve the best variant the
browser accepts, plus gzip for JSON API responses over ~1 KB.
Cloudflare compresses at its edge once the tunnel is live, but the
connection from the tunnel to Nook and all home-network use stay
uncompressed.
**Effect:** first load ~1.27 MB → ~0.35 MB transferred.

### 2. Shrink the main bundle (S–M)
Two things land in the main bundle that the first screen never needs:
- **Icon picker data.** `lucideIcons.ts` pulls in `lucide-static/tags.json`
  (261 KB of search keywords) and URL/loader maps for all 2077 icons.
  Only the icon picker needs those. `PageIcon` only needs "load the
  SVG of this one icon by name". Split the module: keep a small
  name → loader map for `PageIcon`, move tags and the URL map into
  the lazy IconPicker chunk.
- **Realtime editing library.** `App.tsx` imports one small function
  (`setCollabUser`) from `collabProvider.ts`, which drags Yjs,
  y-tiptap and parts of ProseMirror into the main bundle. Move the
  collab user name/color into a tiny module of its own, so all of Yjs
  loads with the editor chunk.

**Effect:** estimated main bundle 1.2 MB → 0.4–0.5 MB raw; faster parse
on phones, where JS parsing is several times slower than on this
server.

### 3. Open pages without the sequential waits (S)
Opening a page today runs three steps in a row: fetch the whole page,
including its full content, then load the editor chunk the first
time, then connect the realtime socket and sync. With realtime editing
the content arrives through the socket anyway, and `initialContent`
only matters the first time a page is ever opened.
- Preload the editor chunk right after login, while the browser is idle.
- Fetch page metadata and connect the socket in parallel, instead of
  mounting the editor only after the full `GET /api/pages/{id}`.

**Effect:** first page open ~900 ms → ~200–300 ms, switching ~200 ms
→ ~100 ms (estimates).

### 4. Sidebar tree without page bodies, in one request (S–M)
`pages.ListForSpace` selects `content_json` for every page of a space,
and the handler then throws it away to build the tree. Every sidebar
load reads every page body in the database. This is invisible at 100
pages and slow at a few thousand. Add a tree query without
`content_json`. Also, the startup loads each space's tree in its own
request, 6 requests today, one per space. A single
`GET /api/tree` returning all visible spaces would make that one
request.

### 5. SQLite tuning (S–M)
- `PRAGMA synchronous = NORMAL`: in WAL mode this stays crash-safe for
  the database (a power cut can lose only the last moment of commits)
  and cuts the fsync cost of every write.
- Today one connection serves all reads and writes
  (`SetMaxOpenConns(1)`). Realtime editing writes an update row on
  every edit, and every sidebar load, search and page fetch queues
  behind it. A second, read-only pool of a few connections lets WAL
  do what it is good at: readers never wait for the writer.
- Also worth adding: `temp_store = MEMORY`, a larger `cache_size`.

**Effect:** small today, matters with two people typing at once and
more content.

### 6. Rate limiting per session for logged-in users (S–M)
The general limit is 10 requests/s with a burst of 30 per IP address.
Two people at the same home share one public IP, so they share one budget.
Opening the app alone uses ~12 requests. While measuring I easily
triggered 429 errors, including on search. Keep the strict per-IP
limit for logins and anonymous requests, and budget logged-in requests
per session.

## Fluidity in the interface

### 7. Fewer re-renders (M)
There is no `memo`, `useMemo` or `useCallback` anywhere in `App.tsx`,
`Sidebar.tsx`, `Editor.tsx` or `DatabaseView.tsx`. Every state change
in `App` re-renders the whole 1600-line sidebar tree, for example a
page loading, a tab switch, or the new approvals poll. Not visible
with 13 sidebar rows, but noticeable with hundreds. Wrap sidebar rows
and sections in `memo`, give `App`'s callbacks stable identities, and
measure with the React Profiler before and after.

### 8. Large databases: virtualized rows (M)
`DatabaseView` renders every row. Fine for dozens of rows, slow for
hundreds. Render only the visible rows. Do this when a real database
gets big, not before.

### 9. Small touches
- Restore open tabs after a refresh (localStorage). Today a refresh
  always lands on the empty start screen. (S)
- Prefetch a page when hovering over its sidebar row. (S)
- Show a short message instead of silently failing when the server
  answers 429. (S)

## Code health and refactoring

### 10. Split the largest files (M each)
| File | Lines | Suggested split |
|---|---|---|
| `frontend/src/Sidebar.tsx` | 1598 | tree rendering, group section, space section, drag-and-drop hook, row menus |
| `frontend/src/App.tsx` | 759 | a `useWorkspace` hook (spaces, pages and their mutations) and a `useTabs` hook (which also makes item 9's tab restore easy) |
| `frontend/src/DatabaseView.tsx` | 877 | table, header and column menus, row logic |
| `backend/internal/httpapi/accounts.go` | 817 | public auth flows, self-service profile and sessions, admin endpoints |

This is not about line counts. These files mix several jobs, and
each change risks breaking something unrelated.

### 11. Frontend tests (M)
The backend has 139 Go tests. The frontend has none. Two cheap layers:
- **Vitest** for pure logic: tree operations in `sidebarData.ts`, icon
  string parsing in `pageIcon.ts`, `urlTokens.ts`.
- **Playwright smoke tests:** headless Chromium works on this server
  now. Cover login, opening a page, typing, the database view, and the
  phone layout. Most of the browser checks run by hand during this
  session could become these tests.

### 12. Already on the roadmap, confirmed by this pass
- Sweep unreferenced uploaded files. Deleted pages, and since today
  deleted accounts, leave their image files on disk.
- Make dependency scanning recurring (`govulncheck`, `npm audit`).

## Suggested order

1. Items 1–3 together: compression, bundle split, faster page open.
   Mostly delivery changes, low risk, biggest felt difference.
2. Item 4 and item 5: tree query and SQLite tuning.
3. Item 6, before more people use the instance from one household.
4. Item 9's tab restore, then 7 and 10 together. Splitting the files
   is the natural moment to add memoization.
5. Item 11 alongside all of the above, so each change gets a test.
